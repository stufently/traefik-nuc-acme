На каждой порче выполнены дословные команды **M4 AC-001…AC-009**, все девять,

До кампании все девять поведенческих критериев прошли на оригинале; после
восстановления они также прошли. Сбоев среды, заблокировавших кампанию, не было.

M4 AC-010…AC-012 запускались отдельной группой до кампании и после неё,

восстановлен; вручную апстрим и патч не редактировались.

- **M15:** AC-002 = 4, `испорченный пресет принят`: обвязка скрыла код ошибки.

## Чего не хватает для каждой выжившей порчи

**M01 — сравнение только первых восьми hex-символов sha256.**
AC-006 проверяет пин из 64 нулей: его первый фрагмент уже отличается, и
мутант честно отказывает. Не хватает неверных пинов с правильным префиксом
и изменённым хвостом, отдельно для обоих сертификатов. В дополнительном опыте
менялся только последний символ настоящего пина: оригинал возвращал 1 и не
создавал цель, M01 возвращал 0 и создавал бандл — для корня и Sub CA.
Контроль целостности сокращается с 256 до 32 сравниваемых бит.

**M04 — неатомарная запись в файл назначения.**
AC-007 сравнивает два успешно созданных разных файла, AC-006 испытывает ошибку
до финальной записи. Нет сбоя во время замены уже существующего бандла и
проверки сохранения прежних байтов. Дополнительный опыт подставлял отдельный
`cat` через PATH: только при чтении `*/bundle.pem` он записывал 32 байта и
возвращал 73; остальные вызовы передавались системному `cat`.
Оригинал и мутант вернули 73, но оригинал сохранил прежний файл, а M04 оставил
`-----BEGIN CERTIFICATE-----\nMIIF`. Последствие — повреждение рабочего бандла
при сбое записи и возможность увидеть частичный файл при конкурентном чтении.
Эта инъекция использовалась только в дополнительном опыте, не в девяти AC.

**M05 — удаление существующей цели до загрузок и проверки пинов.**
В AC-006 путь всегда новый; нет сценария «рабочий бандл уже существует,
обновление не удалось». На заранее записанном контрольном файле с неверным
Sub CA-пином оригинал и M05 вернули 1 с сообщением sha256 mismatch, но только
оригинал сохранил файл: после M05 его нет. Не хватает проверки сохранения
существующей цели на каждом отказе. Ошибка при обновлении уничтожает рабочее
доверенное хранилище и может сорвать следующий запуск или TLS-соединение.

**M06 — потеря очистки каталога загрузок после успешной сборки.**
AC-006 осматривает только каталог назначения при неверном пине, а не TMPDIR
после успешной сборки. Отдельный запуск с выделенным TMPDIR дал rc=0 в обоих
случаях: оригинал оставил его пустым, M06 оставил каталог с шестью файлами
(`root.crt`, `sub.crt`, `root.pem`, `sub.pem`, `bundle.pem`, `openssl.err`).
Не хватает проверки уборки обоих временных расположений на успехе и ошибке.
Последствие — накопление файлов и расход места при регулярных обновлениях;
сертификаты публичные, утечка секретов этим опытом не показана.

**M11 — путь `caCertificates` не совпадает с монтированием из README.**
AC-005 проверяет бандл в своём временном каталоге; AC-008 монтирует только
пресет и запускает гвард Subject, который не открывает CA-файл. Не хватает
совместного прогона документированного монтирования и пути, реально указанного
в пресете. В контейнере с документированным mount проверка `test -r` исходного
пути вернула 0, пути мутанта `/etc/traefik/ca/nuc.pem` — 1. ACME-провайдер
передаёт эти пути в `lego.CreateCertPool` (`pkg/provider/acme/provider.go:422`),
поэтому такой пресет лишается доступного файла доверия.

**M12 — HTTP challenge ссылается на отсутствующий entryPoint `http`.**
В пресете объявлены только `web` и `websecure`. Все AC пропустили эту ссылку.
Не хватает проверки, что entryPoint challenge существует и что маршрут
`acme-http@internal` действительно к нему привязан. Вывод о последствиях
подтверждён чтением апстрима: `pkg/provider/traefik/internal.go:119` переносит
имя в router, а `pkg/config/runtime/runtime_http.go:31` и `:49` отвергают
отсутствующий entryPoint и маршрут без действующих entryPoints.
Обработчик HTTP-01 не получит рабочего маршрута; живой выпуск для этого
вывода не выполнялся и не нужен.

**M13 — README монтирует CA в `/etc/traefik/ca/ca.pem`, пресет ждёт другой файл.**
Это независимая ошибка инструкции запуска. AC-009 ищет только AIA и
предупреждение UNVERIFIED; docker-команда из README не проверяется вместе
с пресетом. При таком mount контейнерный `test -r` ожидаемого пресетом файла
вернул 1, с исходным mount — 0. Не хватает проверки документированного
сценария как целого. Пользователь, следующий инструкции, получит недоступный
CA-файл и отказ инициализации доверия к ACME-серверу.

**M14 — `exec "$bin" $@` вместо `exec "$bin" "$@"`.**
Все аргументы AC-001/002 не содержат пробелов; потеря границ аргументов
остаётся незаметной. Не хватает прогона с путём конфигурации, содержащим
пробелы, и проверки причины ошибки. В дополнительном опыте один и тот же
файл `config with spaces.yml` содержал `country: RUS`: оригинал дошёл до него
и вернул 1 с `invalid CSR subject in resolver`, M14 вернул 1 из декодера
флагов (`field not found, node: configfile`). Одинаковый rc здесь не означает
одинакового поведения. Следствие — обвязка ломает корректно переданные
аргументы с пробелами; некавыченный `$@` также допускает glob-расширение.

**Опаснее прочих M01.** Он ослабляет единственный контроль целостности
промежуточного сертификата, скачиваемого по HTTP, и при этом проходит даже
усиленный AC-006 с двумя неверными пинами. Сравниваются всего 8 hex-символов:
это 32 бита, то есть пространство из 2^32 префиксов вместо проверки всех
256 бит. Подмена доверенного материала затрагивает аутентификацию CA, тогда
как остальные показанные порчи прежде всего нарушают доступность или уборку.
Опыт доказал принятие неверных пинов; подбор коллизии префикса и MITM-атака
против живого НУЦ не проводились.

## Два утверждения о живом TLS

Проверен адрес `https://nuc-acme.voskhod.ru/acme/api/v1/directory`.
`curl` запускался с явным `--cacert`, без `-k`, с ограничением 60 секунд.

| Доверенный материал | rc curl | ssl_verify_result | HTTP |
|---|---:|---:|---:|
| Только корень с gu-st.ru | 60 | 20 | 000 |
| Бандл скрипта: корень + Sub CA 2024 | 0 | 0 | 200 |

Полученный JSON содержит `newNonce`, `newAccount`, `newOrder`, `revokeCert`,
`keyChange` и `meta: null`. Сервер прислал один сертификат — лист.
**Первое утверждение подтверждено:** одного корня в этой проверке недостаточно,
полный бандл валидирует TLS и позволяет получить директорию.

| Объект | Серийный номер (hex) | Идентификатор ключа |
|---|---|---|
| Текущий лист | `44EE059130D849C4861CB2CEA1408050` | AKI `77:3D:D9:39:AF:42:BD:DC:5B:CA:76:EA:EE:FD:CE:3E:61:29:30:5F` |
| Sub CA 2024 из AIA | `1005` | SKI `77:3D:D9:39:AF:42:BD:DC:5B:CA:76:EA:EE:FD:CE:3E:61:29:30:5F` |
| Sub CA 2022 с gu-st.ru | `1002` | SKI `D1:E1:71:0D:0B:2D:81:4E:6E:8A:4A:8F:4C:23:B3:4C:5E:AB:69:0B` |

AIA листа содержит `http://nuc-cdp.voskhod.ru/cdp/subca_ssl_rsa2024.crt`.
`openssl verify -CAfile root.pem -untrusted sub.pem leaf.pem` с Sub CA 2024
вернул 0 и `OK`; со старым Sub CA — 2 и `error 20 at 0 depth lookup`.
**Второе утверждение подтверждено:** SKI сертификата `1002` не совпадает с AKI
листа, тогда как SKI сертификата `1005` совпадает. Вывод сделан по ключевым
идентификаторам и проверке цепочки, а не по одинаковым именам издателей.

Команды, аргументы, коды и выводы измерений сохранены в разделе `tls`
машиночитаемого отчёта. Это наблюдение на дату проверки; ротация сертификатов
может изменить будущий результат. Выпуск и продление против боевого НУЦ
не проверялись; требование НУЦ использовать RSA2048 остаётся предположением.

## Повтор кампании

Из чистого клона с тем же продуктом, апстримом и доступной сетью можно
повторить точные замены и девять команд по evidence JSON. Следующий фрагмент
проверяет SHA-256, не меняет критерии и восстанавливает каждый файл в `finally`.
Запускать его отдельно от других гейтов и других изменений этого клона.

```bash
python3 - <<'PY'
from pathlib import Path
import hashlib
import json
import subprocess

e = json.loads(Path("docs/reviews/m4-cross-review-evidence.json").read_text())
commands = e["m4_commands"]
sha = lambda data: hashlib.sha256(data).hexdigest()
def run(cid):
    return subprocess.run(commands[cid], shell=True).returncode
for cid in ("AC-010", "AC-011", "AC-012"):
    assert run(cid) == 0, cid
try:
    for m in e["mutations"]:
        p = Path(m["file"])
        original = p.read_bytes()
        assert sha(original) == m["original_sha256"]
        old = m["before"].encode()
        assert original.count(old) == 1
        changed = original.replace(old, m["after"].encode(), 1)
        assert changed != original and sha(changed) == m["mutated_sha256"]
        try:
            p.write_bytes(changed)
            assert p.read_bytes() == changed
            codes = [run(f"AC-{i:03}") for i in range(1, 10)]
            print(m["id"], codes, "убита" if any(codes) else "выжила", flush=True)
        finally:
            p.write_bytes(original)
            assert p.read_bytes() == original
            assert sha(p.read_bytes()) == m["restored_sha256"]
finally:
    for cid in ("AC-010", "AC-011", "AC-012"):
        assert run(cid) == 0, cid
PY
```

## Приёмка обзора (координатор, 2026-09-07)

Обзор принят целиком: 5/5 критериев перекрёстной проверки перегнаны
независимо, продукт и апстрим восстановлены побайтово, оба утверждения о живом
TLS подтверждены по ключевым идентификаторам, а не по именам издателей.

Восемь выживших — дыры в МОИХ критериях, не в работе исполнителя. Семь закрыты
`scripts/nuc_preset_checks.sh`; каждая проверка доказана тем, что убивает свою
порчу:

| порча обзора | что теперь ловит |
|---|---|
| M01 сравнение пина по префиксу | пин, отличающийся ТОЛЬКО последним символом, для обоих сертификатов |
| M05 удаление цели до проверки | существующий бандл обязан пережить неудачное обновление |
| M06 остатки в TMPDIR | пусто и на успехе, и на ОТКАЗЕ |
| M11 путь `caCertificates` | совпадение с путём монтирования из README |
| M13 монтирование из README | та же проверка с другой стороны |
| M12 challenge на чужой entryPoint | entryPoint challenge обязан быть объявлен |
| M14 потеря границ аргументов | путь конфигурации с пробелом обязан дойти до гварда |

Диагноз M01 как самой опасной верен и подтверждён отдельно: единственный
контроль целостности файла, качаемого по HTTP, сокращался с 256 бит до 32, и
усиленный критерий с двумя нулевыми пинами его пропускал — нулевой пин
отличается уже в префиксе.

Проба M06 сначала выжила и у меня — по содержательной причине: мой же фикс
атомарности добавил второй `trap`, поэтому удаление первого больше не ломает
путь успеха, а течь осталась на пути ОТКАЗА, до установки staging-ловушки.
Проверка расширена на оба пути, после чего порча убита.

**Не закрыт сознательно один: M04, неатомарная запись.** Ловля требует сбоя
посреди финальной записи (инъекция `cat` через PATH, как в обзоре). Цена
регрессии: при сбое портится рабочий бандл и чинится повторным запуском
скрипта, который и так пишет через staging с переименованием. Оценённый
пробел, не долг — вехи он не стоит.
