## Задача и почему

`scripts/stand.sh renew-check` (строки 248–284) недетерминирован: пять прогонов
на приёмке вехи M6 дали **три отказа и два успеха**. Отказ выглядит так:

```
acme: error: 403 :: urn:ietf:params:acme:error:unauthorized :: Non-200 status
code from HTTP: http://stand.traefik-nuc.test:5002/.well-known/acme-challenge/…
returned 404
…
timeout waiting for renewed serial and new captured CSR (still <serial>)
```

Механика (проверено чтением кода, см. ниже): `cmd_renew_check` делает РОВНО ОДИН
`compose up -d --force-recreate --no-deps traefik` и ждёт нового серийника до
`STAND_RENEW_TIMEOUT` (по умолчанию 180 с). Traefik продлевает сертификат один
раз при старте, а следующую попытку делает по тикеру `renewInterval`, который
при `certificatesDuration: 8760` равен **168 часам**. Значит один проигранный
ACME-челлендж (гонка между стартом продления и готовностью маршрута
`/.well-known/acme-challenge/`) гарантированно уводит прогон в таймаут: второй
попытки внутри окна не будет НИКОГДА.

Из-за этого критерий вида «стенд продлевает сертификат» падает примерно в
половине прогонов по причине, не связанной с проверяемым кодом. Веха чинит
именно это: отказ по известной гонке должен приводить к НОВОЙ попытке, а любой
другой отказ — падать сразу и по своей причине.

🚨 Правку `certificatesDuration` как решение НЕ рассматривать: в
`getCertificateRenewDurations` период продления и интервал попыток берутся ОДНОЙ
веткой switch, и любое уменьшение `certificatesDuration` ужимает и период —
traefik просто перестанет считать сертификат подлежащим продлению, и
`renew-check` сломается совсем. Это проверено чтением таблицы, а не догадкой.

## Что проверено вживую, а что предположение

| Утверждение | Чем подтверждено |
|---|---|
| `renew_timeout="${STAND_RENEW_TIMEOUT:-180}"` | `scripts/stand.sh:15` |
| `cmd_renew_check` делает один `--force-recreate` и один цикл ожидания | тело функции, `scripts/stand.sh:248-284` |
| `docker/traefik.yml:18` задаёт `certificatesDuration: 8760` | grep по файлу |
| при `certificatesDuration >= 365*24` интервал попыток = `7*24h` | `getCertificateRenewDurations`, апстрим `pkg/provider/acme/provider.go` |
| образ `traefik-nuc-acme:3.7.13-nuc.1` есть в локальном докере | `docker images` |
| текст отказа с `urn:ietf:params:acme:error:unauthorized` и `404` | лог прогона живого стенда на приёмке M6 |
| 3 отказа из 5 прогонов | замер постановщика 07.09.2026 |

**Предположение (проверять не требуется, на решения не влияет):** срок жизни
сертификата, который выдаёт Pebble, меньше четырёх месяцев — иначе traefik при
`renewPeriod = 4 месяца` не считал бы его подлежащим продлению вовсе. Значение
нигде не задаётся, берётся умолчание образа.

## Что сделать

Только `scripts/stand.sh`, плюс новые файлы-фикстуры и запись в `CHANGELOG.md`.

1. **Вынести классификацию отказа в отдельную функцию и в подкоманду.**
   Новая подкоманда `classify-renew-log <файл>`: возвращает **0**, если в логе
   есть подпись известной гонки — ОДНОВРЕМЕННО `urn:ietf:params:acme:error:unauthorized`,
   `/.well-known/acme-challenge/` и `404` в одной строке, — и **ровно 1** в
   любом другом случае (код 1 проверяется критерием, другой ненулевой не
   годится). Ровно эта функция решает, повторять попытку или нет.
   Классификатор обязан быть чистым: читает файл, ничего не поднимает.
2. **Повтор в `cmd_renew_check`.** Число попыток — `STAND_RENEW_ATTEMPTS`,
   по умолчанию **3**. Каждая попытка: `--force-recreate` traefik, ожидание до
   `STAND_RENEW_TIMEOUT`, и при истечении окна — сохранить лог traefik этой
   попытки во временный файл и спросить классификатор.
   - классификатор сказал «гонка» и попытки ещё есть → следующая попытка,
     в stderr строка вида `renew attempt N/M lost the ACME challenge, retrying`;
   - классификатор сказал «не гонка» → **падать немедленно**, печатая лог;
     повтор здесь запрещён, иначе веха замаскирует настоящую регрессию;
   - попытки кончились → падать, напечатав, сколько их было и по какой причине
     каждая проиграла.
3. **Прежние жёсткие отказы не смягчать.** Нет сертификата в хранилище
   (`no certificate to renew…`), traefik умер во время ожидания, CSR без `C=RU` —
   всё это по-прежнему немедленный отказ без повторов.
4. **Фикстуры** в новом каталоге `docker/testdata/`: `renew-log-retryable.txt`
   (реальная строка отказа из шапки этой спеки) и `renew-log-other.txt` (любой
   другой отказ traefik — например падение резолвера или отказ CA без
   `acme-challenge`). Файлы маленькие, по несколько строк.
5. **`usage()`** — дописать `classify-renew-log` в список подкоманд и перечислить
   переменные окружения `STAND_WAIT_TIMEOUT`, `STAND_RENEW_TIMEOUT`,
   `STAND_RENEW_ATTEMPTS` с их умолчаниями.
6. **`CHANGELOG.md`** — запись за 2026-09-07 о том, что `renew-check` повторяет
   попытку ровно на известной гонке ACME-челленджа и падает сразу на любом
   другом отказе.

## Критерии приёмки

Каждый критерий возвращает 0, когда он ВЫПОЛНЕН, и проверяет причину, а не
только код возврата.

- **AC-001** — классификатор узнаёт известную гонку:
  `bash -c 'scripts/stand.sh classify-renew-log docker/testdata/renew-log-retryable.txt'`
- **AC-002** — и НЕ считает гонкой любой другой отказ:
  `bash -c 'test -f docker/testdata/renew-log-other.txt || { echo "нет фикстуры" >&2; exit 1; }; scripts/stand.sh classify-renew-log docker/testdata/renew-log-other.txt; rc=$?; [ "$rc" -eq 1 ] || { echo "ожидался код 1, получен $rc" >&2; exit 1; }'`
- **AC-003** — 🚩 пять прогонов подряд зелёные. Долгий критерий (минуты),
  Docker обязателен:
  `bash -c 'scripts/stand.sh down >/dev/null 2>&1; scripts/stand.sh up && scripts/stand.sh wait && for i in 1 2 3 4 5; do scripts/stand.sh renew-check || { scripts/stand.sh down >/dev/null 2>&1; echo "прогон $i упал" >&2; exit 1; }; done; scripts/stand.sh down >/dev/null 2>&1'`
- **AC-004** — пустое хранилище по-прежнему отказ без повторов:
  `bash -c 'scripts/stand.sh down >/dev/null 2>&1; out=$(scripts/stand.sh renew-check 2>&1); rc=$?; printf "%s\n" "$out"; [ "$rc" -ne 0 ] && printf "%s" "$out" | grep -qF "no certificate to renew"'`
- **AC-005** — подкоманда и переменные описаны в usage:
  `bash -c 'u=$(scripts/stand.sh --help); for k in classify-renew-log STAND_RENEW_ATTEMPTS STAND_RENEW_TIMEOUT; do printf "%s" "$u" | grep -qF "$k" || { echo "usage не упоминает $k" >&2; exit 1; }; done'`
- **AC-006** — запись в журнале изменений:
  `bash -c 'grep -qF "renew-check" CHANGELOG.md'`
- **AC-007** — дерево чистое и никаких GitHub Actions:
  `bash -c 'test -z "$(git status --porcelain -- . ":(exclude)report.json" ":(exclude)report-blocked.md")" && test -z "$(git ls-files -- ".github")" && test ! -d .github'`

## Контракт отчёта

`report.json` в корне клона:

```json
{"criteria": [{"id": "AC-001", "status": "pass|fail|blocked",
               "command": "<команда-доказательство>", "rc": 0, "note": "…"}]}
```

Записей ровно столько, сколько критериев. `blocked` — штатный исход, когда среда
не даёт выполнить критерий: в `command` — команда-улика, в `note` — дословная
ошибка. Обходить несовместимость ЗАПРЕЩЕНО. У AC-003 в `note` приведи для
каждого из пяти прогонов строку `renewed <old> -> <new>` и укажи, сколько
попыток внутри него понадобилось.

## Контракт на невыполнимое

Требование спеки противоречит другому требованию или коду — ОСТАНОВИСЬ, положи
`report-blocked.md` с воспроизведением и фактическими значениями, закоммить его
и доложи. Обходить несовместимость запрещено: тихий обход дороже честной
остановки.

## Авторевью перед отчётом (обязательно)

Закончив работу и получив зелёные критерии, ДО написания report.json:

1. Закоммить всё в клоне (`git add` по именам, никогда `-A`). Ревьюеры ходят в
   клон СВОИМ шеллом и способны прибрать незакоммиченное дерево — тогда гейт
   окажется зелёным не про твой код.
2. Из КОРНЯ КЛОНА запусти ДВА ревью ПАРАЛЛЕЛЬНО (два фоновых вызова):
   bash ~/.claude/skills/ask-codex/scripts/run.sh "result" "<что сделано, какие файлы, какие критерии>"
   bash ~/.claude/skills/ask-agy/scripts/run.sh   "result" "<тот же текст>"
   Оба смотрят репозиторий по ТЕКУЩЕМУ каталогу — из другого каталога отревьюят
   чужой код. Codex обязателен: сбой — один повтор, второй сбой — пиши в отчёт
   `review_codex: "failed: <ошибка>"` и продолжай. agy — soft-fail, при сбое
   просто отметь это в отчёте. agy идёт до 900 с — только фоном.
3. Замечания перепроверь ПО КОДУ, а не принимай на веру: ревьюеры дают ложные
   находки. Настоящие почини в этом же заходе, прогони критерии заново,
   закоммить.
4. Круг исправлений ровно ОДИН. Пришедшее после него НЕ чинь — выпиши в
   `review_backlog`.
5. В report.json добавь поля верхнего уровня:
   "review_codex":   "<вердикт и находки одной-двумя строками>",
   "review_agy":     "<то же; 'принято, находок нет' пиши дословно>",
   "review_backlog": ["<замечание, оставленное без правки>", "…"]
   Пустой список законен. Врать бессмысленно: приёмщик гоняет ревью сам и сверяет.
